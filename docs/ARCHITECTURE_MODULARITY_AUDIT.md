# Architecture and Modularity Audit\n\n**Reviewed:** 2026-11-12\n**Scope:** backend and frontend source under `routes/`, `services/`, and\n`frontend/`. This began as a code-reading audit; implementation status is\nrecorded below. No runtime profiling was performed. Priorities indicate the\nvalue of creating a clearer seam, not proof of a defect.\n\n## Summary\n\nThe code already has useful seams—pipeline stages, a document-type registry,\nconfiguration helpers, storage adapters, and a pure decision-policy module.\nThe main opportunities are places where large modules still own several kinds\nof behavior, or where similar workflows have drifted into separate copies.\nThese increase the effort and risk of adding document types, checklist checks,\nupload modes, and UI routes.\n\nThe suggested direction is incremental extraction behind existing function\nsignatures. Keep security checks, evidence requirements, and loan-review policy\nexplicit and tested. “Dynamic” here means data-driven selection or composition\nat an existing seam; it does not mean moving consequential policy into\nunreviewed configuration or adding a general plugin framework by default.\n\n## Findings\n\n### 1. ZIP and batch upload flows duplicate package orchestration\n\n**Priority:** High\n**Evidence:** [routes/upload.py](../routes/upload.py) contains the prepared\npackage endpoint at `upload_zip_package` (around line 303), mapped-ZIP parsing\nat `_save_mapped_zip_package` (around line 827), batch routing at\n`upload_batch` (around line 1547), and another mapped-ZIP unpack/validate/queue\nflow at `_batch_single_mapped_zip` (around line 1940).\n\n**Why this is a modularity issue:** The code repeats archive member filtering,\nPDF/JSON discovery, manifest parsing, PDF selection, bounded extraction,\nstaging, and validation across endpoint and batch paths. The paths have\ndifferent contracts—unordered ZIP preparation versus ZIP plus a trusted\nmanifest—so they cannot safely be collapsed into one opaque handler. However,\nduplicated low-level mechanics can drift in size checks, hidden-file handling,\nerror mapping, and cleanup.\n\n**Direction:** Extract narrow services such as `inspect_zip_members`,\n`read_bounded_member`, `resolve_manifest_pdf`, and `stage_mapped_source`. Keep\nseparate mode-specific policies for package preparation and mapped verification;\ncompose those policies from shared primitives. Make staging cleanup a context\nmanager so every route and batch branch gets the same `finally` behavior.\n\n**Safe first step:** Add parity tests that feed the same archive through the\nsingle-upload and batch paths and compare selected PDF, manifest, and rejection\nreason before moving shared mechanics.\n\n### 2. Checklist engine is a large conditional dispatcher\n\n**Priority:** High\n**Evidence:** [services/checklist_engine.py](../services/checklist_engine.py)\nhas the presence dispatch around lines 835–1047, a second long accuracy\ndispatch beginning at `_run_accuracy_checks` around line 1136, and the public\n`run_checks` coordinator around line 1504. `check_type` branches cover\n`presence`, `requirements`, `field_match`, date/period checks,\n`required_status`, and other cases.\n\n**Why this is a modularity issue:** Adding a check type requires editing a\nshared control-flow function that also handles applicability, person scope,\nanomaly shape, and deduplication. This makes unrelated rule changes conflict\nand makes it difficult to test a check family without importing the whole\nengine.\n\n**Direction:** Keep `run_checks` as the orchestration boundary. Move each\ncheck-family implementation into focused modules or handler functions, and\ndispatch through an explicit registry keyed by the existing `check_type`.\nPass a typed context containing pages, trusted data, product, and anomaly\nbuilder. Validate unsupported check types clearly instead of silently\naccepting them.\n\n**Boundary:** Checklist definitions and loan-review rules remain versioned,\nreviewable policy. A registry should select vetted Python handlers; it should\nnot turn arbitrary JSON into executable conditions or move safety decisions\nto an unreviewed database setting.\n\n### 3. Mapped verification combines too many domain stages\n\n**Priority:** High\n**Evidence:** [services/mapped_verification.py](../services/mapped_verification.py)\nis about 2,000 lines. It includes field comparison (`_verify_supported_field`,\nnear line 60), the public mapped verification flow (`run_mapped_verification`,\nnear line 280), page comparison (`compare_processed_pages`, near line 692),\ndocument classification (near line 1282), OCR recovery (near line 1389),\nmapping/person resolution (near lines 1631–1749), and anomaly construction\n(near line 1846).\n\n**Why this is a modularity issue:** Parsing/normalizing manifest inputs,\nclassifying source documents, extracting trusted fields, matching values,\nresolving person ownership, and building result anomalies are different\nreasons to change. Their current shared module makes independent policy\nchanges difficult to isolate and unit-test.\n\n**Direction:** Preserve the public facade, then extract pure pieces in this\norder: canonical field comparison; expected-field/person resolution; source\ndocument classification; OCR-based trusted-field recovery; final orchestration.\nUse small typed inputs/outputs between stages and keep provenance attached to\neach recovered value.\n\n**Risk to guard:** Do not let extraction-derived values silently become trusted\nmanifest values. Keep provenance, ambiguity, and person ownership explicit at\nthe module boundaries.\n\n### 4. Consistency checks mix rule families and shared mechanics\n\n**Priority:** High\n**Evidence:** [services/consistency_checks.py](../services/consistency_checks.py)\nis about 2,250 lines. `run_consistency_checks` starts around line 496 and\ncollects observation data; separate rule families include identity/address\nmatching, bureau checks, affidavits, relationship checks, application-name\nchecks, and language checks (for example `_relationship_checks` around line\n1350, `_bureau_checks` around line 1563, and `_application_language_checks`\naround line 1840).\n\n**Why this is a modularity issue:** A single entry point coordinates many\ndomain families while shared normalization and evidence helpers are interleaved\nwith rule-specific behavior. This makes new validation families harder to\nreview and increases the chance that a shared helper change alters unrelated\nchecks.\n\n**Direction:** Introduce a `ConsistencyContext` built once from pages and\ntrusted data (normalized page text, observations, page lookup, people, and\nreference date), then move each rule family behind a small function/module\nthat consumes that context and returns anomalies. Keep the current aggregation\norder and anomaly schema stable during extraction.\n\n### 5. Person ownership contains multiple resolver strategies in one module\n\n**Priority:** Medium-high\n**Evidence:** [services/person_ownership.py](../services/person_ownership.py)\nis about 1,550 lines. It contains trusted-person parsing and ownership\nassignment, CERSAI document grouping and debtor/asset logic, filename overrides,\nidentity scoring and conflict checks, relationship observations, banking\nholder-name extraction, and value normalization. The main assignment path is\n`assign_page_owners` around line 568; text-observation helpers occur later in\nthe file.\n\n**Why this is a modularity issue:** Generic person scoring and document-family\nspecial cases are coupled. Adding a new document type or identity evidence\nsource risks changing behavior for unrelated documents.\n\n**Direction:** Keep a single public owner-resolution facade, but make its\nstrategy stages explicit: trusted/manifest owner, grouped-document resolver\n(such as CERSAI), source-filename evidence, identity evidence, and conservative\nfallback. Extract CERSAI and banking observations into focused modules first.\nReturn a common result shape with owner, confidence, evidence, and scope.\n\n**Risk to guard:** Preserve conservative `unassigned` behavior. A strategy\nregistry must not turn missing evidence into an implicit primary-applicant\nassignment.\n\n### 6. Classifier registry is partly bypassed by type-specific ranking logic\n\n**Priority:** Medium\n**Evidence:** [services/document_classifier.py](../services/document_classifier.py)\nloads a registry and scores candidate rules, but `classify_page_with_candidates`\ncontains additional named-type handling for Aadhaar, Application Form,\nInsurance Form, and Bank Statement around lines 257–277.\n\n**Why this is a modularity issue:** Registry edits alone do not fully explain\nclassification behavior: some post-scoring corrections are encoded in Python\nconditionals. A maintainer adding or tuning a type must know to inspect both\nthe registry and code.\n\n**Direction:** Make post-scoring adjustments explicit metadata or ordered,\nnamed post-processors selected by type. First document every current override\nand add tests for tie/override ordering; then migrate one override family at a\ntime. Keep the scoring algorithm shared.\n\n**Boundary:** Do not move normalization, security limits, or subtle\nhigh-confidence disambiguation into unchecked data. Registry schema should\nremain validated and versioned.\n\n### 7. Ops presentation service owns data access, storage, mapping, and copy\n\n**Priority:** Medium\n**Evidence:** [services/ops_presentation.py](../services/ops_presentation.py)\nincludes database loaders (`_load_application` through `_load_checklist_context`,\naround lines 351–476), object-store assessment loading near line 206,\nrule-to-operations-code mapping near line 106, bilingual summaries, checklist\npresentation, and the top-level `build_ops_payload` near line 569.\n\n**Why this is a modularity issue:** Persistence changes, operations vocabulary\nchanges, and text/presentation changes converge in one service. That makes\npayload behavior harder to test as pure data transformation and encourages\nextra queries from presentation code.\n\n**Direction:** Separate an ops repository that loads a typed snapshot, a\nfinding mapper that applies the code/severity vocabulary, and a presenter that\nformats summaries/checklist rows. Keep the endpoint payload schema in one\ncontract/test. Have the service assemble the snapshot once and pass it through\nthe pure mapping layers.\n\n### 8. Frontend API client is a domain-wide catch-all\n\n**Priority:** Medium\n**Evidence:** [frontend/lib/api.ts](../frontend/lib/api.ts) is close to 1,000\nlines and mixes shared fetch/auth handling, Zod schemas and types, login/session,\nupload/batch, review/worklist, settings, LLM, admin users, and operations\nendpoints.\n\n**Why this is a modularity issue:** A change in one endpoint family requires\nsearching and editing a large shared file; shared transport and domain response\nschemas have different change cadence. It also makes ownership boundaries less\nclear.\n\n**Direction:** Keep one shared authenticated transport (`request`, error\nmapping, token provider). Move schemas and endpoint functions into domain\nmodules (`api/review`, `api/upload`, `api/settings`, `api/ops`, `api/admin`)\nand preserve a compatibility barrel for current imports. Split incrementally\nto avoid a repository-wide import rewrite.\n\n### 9. Decision component mixes UI state, clock behavior, and action workflow\n\n**Priority:** Medium\n**Evidence:** [ManualReviewAndDecision.tsx](../frontend/components/applications/ManualReviewAndDecision.tsx)\nis about 515 lines and owns undo countdown state, task/page mapping, decision\nsubmission and undo, request-document/override details, and rendering. There is\nalready a separate [decisionPolicy.ts](../frontend/lib/decisionPolicy.ts), so\npart of the policy seam exists.\n\n**Why this is a modularity issue:** The component remains responsible for\nworkflow state and transport as well as rendering, which makes it harder to\ntest asynchronous/error paths separately from presentation.\n\n**Direction:** Keep `decisionPolicy.ts` as the pure allow/deny rule authority.\nExtract a decision-workflow hook for mutations, undo/countdown lifecycle, and\npending/error state; split the large action panels into presentational\ncomponents. The hook should call the existing API and never duplicate policy\nchecks.\n\n### 10. App shell routing and navigation rules are hand-coded in multiple helpers\n\n**Priority:** Medium-low\n**Evidence:** [frontend/components/AppShell.tsx](../frontend/components/AppShell.tsx)\ncombines session-aware shell composition, admin health polling, title resolution,\nactive navigation detection, application submenus, and icon rendering. Route\nrecognition is implemented in helpers such as `resolveHeaderTitle` (around line\n311) and `isNavItemActive` (around line 335) using repeated pathname checks.\n\n**Why this is a modularity issue:** Adding or renaming a route may require\nseparate edits to title, active-state, and navigation logic. Those rules can\ndrift.\n\n**Direction:** Define typed navigation entries with role visibility, route\nmatcher, title, and parent grouping, then derive the sidebar and active/title\nstate from that source. Keep the shell layout and role authorization separate;\nclient navigation metadata must not replace backend access control.\n\n### 11. Pipeline coordinator can be thinner at the stage boundary\n\n**Priority:** Medium-low\n**Evidence:** [services/pipeline/orchestrator.py](../services/pipeline/orchestrator.py)\nhas a public `run_pipeline` wrapper and a roughly 400-line `_run_pipeline_impl`\nstarting near line 100. It coordinates stage execution, recovery branches,\nmanifest handling, page ownership, persistence, progress, and finalization.\n\n**Why this is a modularity issue:** Although some stage modules already exist,\nthe coordinator also performs stage-specific transformations and recovery\ndecisions, so the stage interfaces are not the only source of pipeline flow.\n\n**Direction:** Treat this as a later refactor after stage contracts are stable.\nMove each recovery branch next to the stage it recovers, and make the\norchestrator pass a typed run context and consume stage results. Keep\ncheckpoint/job lifecycle ownership centralized unless there is a clear\ntransactional contract for moving it.\n\n## Suggested extraction order\n\n1. Add behavior/contract tests around the duplicated mapped-ZIP paths and\n   extract their shared low-level helpers.\n2. Split `ops_presentation` into snapshot loading and pure presentation.\n3. Establish the checklist handler registry for existing check types without\n   changing rule definitions or ordering.\n4. Extract mapped-verification pure matching and source classification.\n5. Build a shared consistency context and split rule families.\n6. Separate person-ownership evidence strategies, beginning with CERSAI.\n7. Split frontend API domains behind the shared transport and compatibility\n   barrel.\n8. Extract the decision workflow hook and data-driven shell navigation.\n9. Refactor pipeline orchestration only after stage and checkpoint contracts\n   are covered by tests.\n\n## Review notes\n\n- Large file size alone is not proof that a module needs splitting; boundaries\n  should follow independent reasons to change and stable inputs/outputs.\n- Not all literals are bad hard-coding. Limits and business rules that are\n  security-sensitive or policy-significant should stay explicit, validated,\n  and covered by tests. Make values configurable only when operators have a\n  real supported use case and a clear safe range.\n- The report identifies candidate seams, not authorization to change runtime\n  behavior. Each extraction should preserve output schemas, ordering, evidence\n  provenance, and failure semantics.\n\n## Implementation status: `codex/modularity-refactor`\n\nThe branch implements initial, compatibility-preserving extractions.
